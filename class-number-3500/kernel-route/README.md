# The kernel route: toward a kernel-checked classification of the fields with h ≤ 3500

This directory is the offer made in the comments of Terence Tao's challenge thread: the sieve design and the
per-range certificate format for a **kernel-checked** classification of the imaginary quadratic fields of class
number at most 3500, on the 7/8 footing, split by discriminant range so that several people can take part. It is
written for someone with Lean 4 experience who has not seen this repository before.

Every claim below is labelled **PROVED** (a compiled Lean theorem, cited by file and line), **MEASURED** (a recorded
run, cited), **ESTIMATE** (a calculation from measured constants, with its band) or **OPEN** (not done). Where the
design was never run end to end, it says so. Nothing in this directory has been refereed, and the reviewer referred
to below is a separate AI review session, not a human.

## The goal

Entry 6 of this repository classifies the fields with h ≤ 3500 (50,299,869 fields; the largest |D| is
F = 3,495,584,467) on Kimura's footing (K), by computation that is cross-checked but not kernel-checked. On the
stronger 7/8 footing, the real case of OpenAI's zero-free half-plane Re s > 7/8 (whose Lean proof has been replayed
with two kernels), the goal is the statement

> h(K) ≤ 3500  ⇔  (|disc K|, h(K)) is in the list,

as a Lean theorem over Mathlib, checked by two independent kernels, with only the three standard axioms. It splits
into three pieces:

1. **The threshold.** A kernel-checked X with: |D| ≥ X ⇒ h > 3500. This is entry 5's threshold engine at σ = 7/8,
   one more instance.
2. **The exclusion sieve.** For every fundamental |D| < X not in the list: a kernel-checked h > 3500. This is the
   block sieve of DESIGN.md, in per-range certificates (FORMAT.md).
3. **The certificates for the listed fields.** For each of the 50,299,869 listed fields: a kernel-checked
   h(D) = the listed value.

Pieces 1 and 2 give the range statement "no field of class number ≤ 3500 has |D| > F, except an explicit short
list W"; all three give the classification.

## The three pieces: status

### 1. The threshold (PROVED machinery; the 3500 instance is one theorem away)

Entry 5 proves, in Lean, `lt_classNumber_of_bounds` (`two-sided-bounds/formalization/BoundariesOfClass/Numerics/SevenEighths.lean`):
for rational data (q, r, s, e) satisfying five `norm_num`-checkable inequalities, X ≤ |D| ⇒ N < h. Its instances
(`Numerics/Thresholds.lean`) include X_1000 = 1.605·10^9, X_2000 = 7.8·10^9 and X_5000 = 6.32·10^10, each a
six-line theorem generated by `numerics/gen_T_instances.py`.

The instance for N = 3500 (ESTIMATE, computed here in exact rationals by the same generator logic,
`cost/threshold_3500.py`, output `cost/threshold_3500.out`; NOT yet built in Lean):

```
X_3500 = 28,000,000,000   (q := (1673320053 / 10000 : ℝ)) (r := (13233 / 100000000 : ℝ))
                          (s := (12054553 / 50000000 : ℝ)) (e := (493 / 10000000 : ℝ))     final margin 1.18e-3 > 0
```

(The smallest X on a 10^7 grid at which the rational instance passes is 2.797·10^10; 2.8·10^10 is the natural
round value, with the same margin as the published instances.) The maintainer adds this theorem to `Thresholds.lean` as
`lt_classNumber_of_le_dOf_le_3500`; it then has the same kernel status as the ten published thresholds.

### 2. The exclusion sieve (the soundness library is PROVED; no production range has been run)

The block sieve packs 10^5 consecutive radicands into the bits of one natural number and lets the kernel's native
big-number arithmetic count, for all of them at once, the ideal classes that a small-norm argument proves distinct
(DESIGN.md, sections 1–4). What is PROVED, in `lean/` (eight files, 2,389 lines, compiled 2026-10-25 under Lean
v4.34.1 / Mathlib d13f23b, no `sorry`, standard axioms):

- Lemma 3, `mu_le_classNumber` (`lean/BoundariesOfClass/Sieve/Field.lean:112`): the smooth-norm count is at most h,
  for any field, with no reduction theory;
- the per-field certificate `checkAt` and `lt_classNumber_of_checkAt` (`Check.lean:139, 269`);
- the block certificate `blockOK` and `lt_classNumber_of_blockOK` (`Block/Defs.lean:152`, `Block/Lemmas.lean:670`),
  with the 13 lemmas behind it;
- the range assembly for h ≤ 1000: `Covers`, `ExceptionsOK`, `asmB`, `covers_exceptionsOK_of_asmB`
  (`Block/AsmCheck.lean:94`) and item 8, `dOf_le_or_mem_W18_of_classNumber_le_thousand` (`Block/Lemmas.lean:733`).

What is MEASURED (h ≤ 1000 development, 2026-10-24/25): single generated blocks of 10^5 lanes build in 14–30 s and
9.4–15.8 GB over Y from 7,555 to 20,027; nanoda, a second kernel, accepts correct blocks and rejects a block with one
flipped bit and a closure with a spurious axiom; a Python scan of the whole range F(1000) < d < X_1000 produced 5,165
blocks with 214 exception lanes (18 "W" fields with h from 1002 to 1052, 196 settled by `checkAt`); the assembly ran
end to end at test scale (two blocks, 19 real `checkAt` evaluations) and the negative controls failed as required.
On 2026-11-04 the shipped `lean/` tree was rebuilt from these exact files together with the N = 10 example (`example/`,
17 blocks): build exit 0, standard axioms only, nanoda accepts the exported closure and rejects it with one planted
digit, and the planted digit also fails the Lean build (recorded outputs in example/README.md).

What is OPEN: the h ≤ 1000 production build (5,165 blocks, about 33 CPU-h) was paused before it ran; **no range statement
has yet been kernel-checked at any size**: the N = 10 example stops one unbuilt lemma short (it proves the assembly
check and every block, not the range statement), and the h ≤ 1000 assembly ran only at test scale. The Comparator
replay of a full table was never run. For h ≤ 3500 the Lean needs two mechanical changes (`NP := 12`; the constants N, F, X, W as
parameters: lean/README.md, last section).

### 3. The certificates for the listed fields (OPEN)

Lemma 3 gives lower bounds only. Exact class numbers for 5·10^7 fields need a kernel-checked "h = number of reduced
forms", which does not exist in Lean here or, as far as we know, in Mathlib; DESIGN.md, section 7 gives the design
(Mathlib's fundamental domain for SL(2, ℤ) plus the Hermite normal form already vendored), what exists for small h
(presentation certificates, kernel-checked for h ≤ 2 and built for h ≤ 3), and why the small-h route does not scale.
Until this exists, the kernel route proves range statements, not the classification.

## The cost (ESTIMATE; `cost/cost_model.py`, output `cost/cost_model.out`)

The question in the posted comment was whether "about 25,000 CPU-hours, about one to four months on a single
workstation" stands for the exclusion sieve below the cut-off. The model takes the MEASURED per-block constants
(Lean build 14.0 s at Y = 7,555 and 30.1 s at Y = 20,027; Comparator's Lean-kernel replay 28–43 s and nanoda 8–34 s
above a 7 s overhead; all at L = 10^5 lanes), fits each as affine in Y, and sums over every block below
X = 2.8·10^10 (10.5·10^9 lanes; Y up to 83,666). The table counts every block from m = 3; restricted to the sieve
above F, which is what the verdict below is about, it is 91,894 blocks and 10,184 CPU-h for the four passes at
L = 10^5, about 5% less. Sanity check: run on the real h ≤ 1000 range above F(1000), the same model gives 5,165 blocks
and 33 CPU-h, exactly the recorded production figures.

| kernel pass, below X = 2.8·10^10 | L = 10^5 lanes (105,000 blocks) | L = 2.5·10^4 (420,000 blocks) |
|---|---|---|
| Lean build (one kernel check of every block) | 2,200 CPU-h | 8,900 CPU-h |
| recompile audit (a second build, as the h ≤ 1000 harness does) | 2,200 | 8,900 |
| Comparator replay, Lean kernel | 2,700 | 10,900 |
| Comparator replay, nanoda | 3,600 | 14,400 |
| **all four passes** | **10,800 CPU-h** | **43,000 CPU-h** |
| first design (per-radicand type tree), single pass, interpolated between its N = 2000 and N = 5000 slices | 22,000 CPU-h | — |

The band between the columns is the one unmeasured quantity that matters: RAM per block grows with Y (9.4 GB at
Y = 7,555; 15.8 GB at 20,027; nothing measured above), and if it grows linearly a 10^5-lane block at Y = 84,000
needs about 50 GB, so L must shrink and the per-block overhead multiplies. Not in the table: the shared table (about
4 times the 25 process-minutes of the h ≤ 1000 one), the assembly (minutes), the per-field `checkAt` certificates for
the exception lanes above F (hundreds to thousands of lanes at under a second each), and everything below F.

**Verdict.** "About 25,000 CPU-hours" stands as a central figure for the exclusion sieve above F with the full
two-kernel audit, with a band of roughly 10,000 to 45,000 CPU-h, the band set by memory. As a bare one-kernel figure it
is high by 3–10 times. It is also, to the precision of these estimates, the first design's single-pass cost, which is
probably where the number came from.

"One to four months on a single workstation" does **not** stand for a 32-core, 96 GB machine, and the binding
constraint is memory, not cores (ESTIMATE). Every block above F(3500) has Y ≥ 29,561, where the linear RAM
extrapolation above gives 20.7 GB per process at the bottom of the range and 48.5 GB at the top (L = 10^5): about
82,000 GB-hours per kernel pass. On 96 GB that is at least 1.2 months per pass and about 4.7 months for the four
passes (build, recompile audit, two replays, taking replay RAM equal to build RAM); on 256 GB it is about 1.7 months;
a one-month full audit needs about 450 GB. Shrinking L does not help: if RAM scales with L, the GB-hours are
unchanged and smaller L only adds CPU-hours. Two unmeasured quantities decide the band: whether RAM stays linear in
Y above 20,027, and the affine time fit, which is extrapolated about four times beyond the measured Y.

**Piece 3 (the listed fields):** cannot be costed firmly, because its Lean does not exist. If the reduced-form count
is formalised as designed, the kernel work is about 0.077·√d explicit root checks per field (ESTIMATE 0.1–1 s at
d ≈ 10^9; never run in Lean), so 50.3·10^6 fields are 3,000–10,000 CPU-h for one kernel pass, plus the same again
for the second kernel, plus 1,000–2,000 lines of Lean to write first. "Similar or larger" is consistent with this and
is the most that can be said.

## The cut-off, the ranges, and where the sieve is needed

Above X_3500 = 2.8·10^10, piece 1 settles everything. Between F = 3,495,584,467 and X, the sieve must certify h > 3500
for every fundamental discriminant, about 8·10^9 of them, with the exceptions settled by `checkAt` and a short W list
settled by piece 3. Below F lie all 50,299,869 listed fields (every one is an exception lane of the sieve, by
construction) and about 10^9 fields with h > 3500, of which the block count fails on a few per cent (at N = 1000 it
failed on 3.2 %, MEASURED); those go to `checkAt` at the field's own Y (which settled 87–93 % in two sampled slices)
and the rest to the exact count of piece 3.

On the 7/8 footing nothing above 2^40 is needed at all: entry 5 proves |D| ≥ 2^40 ⇒ h ≥ 17,450, and Mosunov and
Jacobson's unconditional tables cover |D| < 2^40. The kernel route replaces the tables by the sieve, and the sieve's
reach is set by X_3500, not by 2^40.

## How to take part

1. Build the library once: lean/README.md. Report the build time and `#print axioms` of
   `BoundariesOfClass.Sieve.Block.lt_classNumber_of_blockOK`.
2. Build and check the example (example/README.md); send the four expected outputs.
3. Claim a range above F in the ledger (FORMAT.md, section 8), generate it with the shared table of the target,
   build it, run the second kernel on it, run the negative control, and deliver the record of FORMAT.md, section 7.
4. If you would rather write Lean than run it: the parametrised assembly lemma (DESIGN.md, section 6) is hours
   of work for someone with the build; the reduced-form count (DESIGN.md, section 7) is the piece that turns range statements into the
   classification, and it is the one we would most like help with.

Jaswal's; the threshold engine is entry 5's; the block design, the Lean and the generators here were produced with
extensive use of Claude (Anthropic) under the author's direction, with a separate AI review session reviewing each
